# Exposed 1.11 원본 매뉴얼 설계

## 1. 목적과 범위

`bluetape4k/bluetape4k-exposed`가 코드와 함께 관리하는 `docs/manual`을
Exposed 매뉴얼의 source of truth로 확립한다. 첫 공개본은 안정 릴리스
`1.11.0`을 기준으로 하며, 웹사이트는 이 저장소에서 검증을 마친 원본만
불변 minor 스냅샷으로 수집한다.

이 문서는 Exposed 원본 저장소의 책임만 정의한다. 사이트 registry, route,
검색, 배포 구현은 `bluetape4k.github.io`가 소유하고 별도 작업에서 수행한다.

## 2. 고정된 릴리스 권위

```yaml
repository: bluetape4k/bluetape4k-exposed
releaseRef: 1.11.0
releaseCommit: 0b494a5fd1e083006046764757342b68a397e4c5
minorVersion: "1.11"
stableModuleCount: 40
developModuleCount: 42
excludedDevelopOnlyModules:
  - bluetape4k-exposed-druid
  - examples-ddd-spring-modulith-demo
```

현재 `develop`의 42개 Gradle project를 그대로 문서화하지 않는다. 안정 tag에
존재하는 40개 project만 `1.11` 매뉴얼에 포함하고, Druid와 DDD Spring
Modulith demo는 다음 안정 minor가 나올 때까지 제외한다.

## 3. 원본 구조와 소유권

원본 저장소는 다음 구조를 소유한다.

```text
docs/manual/
├── manifest.yaml
├── generated/manifest.json
├── templates/
├── assets/
├── en/
│   ├── index.md
│   ├── getting-started.md
│   ├── architecture/
│   ├── guides/
│   └── modules/
└── ko/
    ├── index.md
    ├── getting-started.md
    ├── architecture/
    ├── guides/
    └── modules/
```

`docs/manual`은 최신 공개 안정 minor의 편집 가능한 정본이다. 이전 minor는
사이트의 불변 스냅샷과 Git 이력으로 보존하며, 다음 안정 릴리스 전까지
`develop` 전용 기능을 현재 안정 매뉴얼에 섞지 않는다.

`manifest.yaml`은 다음 정보를 구조화한다.

- repository identity, release ref, release commit, minor version
- Gradle project path, project name, release tree의 source directory
- `library`, `example`, `benchmark` 유형
- Maven artifact 좌표 또는 비배포 사유
- 영문·한국어 landing과 상세 chapter 경로
- 대표 source, test, example 경로
- diagram source SVG와 rendered PNG
- 공식 upstream 문서와 관련 저장소 metadata

외부 저장소 파일은 manifest의 release-tree 검증 대상으로 넣지 않는다.
workshop이나 JaVers처럼 저장소 경계를 넘는 학습 자료는 일반 Markdown prose
link로 연결하고, 현재 Exposed release tree에 존재하는 것처럼 표현하지 않는다.

## 4. 영문·한국어 계약

영문과 한국어는 다음 항목에서 동등해야 한다.

- 40개 stable Gradle project landing 전체
- index, getting started, architecture, guide, detailed chapter inventory
- version provenance, module facts, code snippets, source links
- diagram inventory와 이미지 배치
- learning path와 관련 저장소 링크

한국어는 직역체가 아닌 실무 기술 문장으로 작성한다. 독자의 문제, 가장 작은
사용 예, 해석, 선택 기준과 주의사항 순서로 설명한다. 영문도 한국어와 같은
사실을 독립적으로 자연스럽게 서술하며, 한 locale에만 중요한 계약이나
예외를 남기지 않는다.

모든 module은 최소한 목적, 선택 시점, 의존성 좌표 또는 비배포 이유, 핵심
API/동작, 대표 source/test, 관련 chapter를 설명하는 landing을 가진다. 핵심
경로는 landing만으로 끝내지 않고 여러 단계의 상세 chapter를 제공한다.

## 5. release inventory와 링크 검증

현재 checkout과 안정 release tree는 서로 다른 권위로 검증한다.

1. Gradle task가 현재 `develop`의 42개 project inventory를 결정적으로 내보낸다.
2. release inventory 도구가 tag `1.11.0`의 build file 존재 여부를 기준으로
   정확한 40개 stable project를 계산한다.
3. manifest의 project 집합과 stable inventory를 양방향 비교한다.
4. 제외 목록은 정확히 `bluetape4k-exposed-druid`와
   `examples-ddd-spring-modulith-demo`여야 한다.
5. release tag가 가리키는 commit이 고정 SHA와 다르면 실패한다.
6. manifest의 repository-relative source, test, example 경로가 release tree에
   실제로 존재하는지 확인한다.
7. 절대 경로, `..` traversal, 현재 checkout에만 존재하는 링크는 거부한다.
8. 모든 검증이 통과한 뒤에만 정규화된 `generated/manifest.json`을 만든다.

release link validator는 문서의 일반적인 외부 URL을 release tree path로
오인하지 않아야 한다. 반대로 GitHub source link가 `develop`, 이동 가능한
branch, 다른 tag를 가리키면 `1.11`의 근거로 인정하지 않는다. 릴리스 코드
링크는 tag 또는 고정 commit으로 해석 가능해야 한다.

## 6. 설치와 중앙 consumer 버전

사용자가 Gradle에 입력하는 버전은 Exposed 저장소의 `1.11.0`이 아니라
`bluetape4k-dependencies`가 제공하는 중앙 consumer 기준선이다. 매뉴얼은
다음 원칙을 지킨다.

- 설치 예제는 중앙 BOM/catalog 사용을 기본 경로로 제시한다.
- 복사 가능한 dependency snippet의 BOM 버전은 문서 생성 시점의 검증된
  `bluetape4k-dependencies` consumer version을 사용한다.
- `1.11`은 이 매뉴얼이 설명하는 Exposed repository release baseline임을
  명시하고, consumer dependency version처럼 보이게 하지 않는다.
- 개별 module 좌표와 BOM 관계를 설명하되 중앙에서 관리하는 버전을
  Exposed 저장소 안에 별도 정책으로 중복하지 않는다.
- 나중에 중앙 BOM이 갱신되더라도 release facts와 source links는 고정된
  `1.11.0` 기준을 유지한다.

## 7. manual-grade 정보 구조

매뉴얼은 README를 잘게 나눈 목록이 아니라, 선택과 적용을 끝까지 안내하는
제품 문서다. 최상위 정보 구조는 다음을 포함한다.

1. 제품 개요, release provenance, 중앙 BOM 설치
2. module 선택 지도와 Build/Learn/Apply repository map
3. Core/DAO와 JDBC/R2DBC repository·transaction 모델
4. JDBC production path와 Spring Boot JDBC 적용
5. R2DBC coroutine path와 Spring Boot R2DBC 적용
6. Caffeine·Lettuce·Redisson cache matrix와 lifecycle
7. Jackson 2/3, Fastjson2, Tink, measured type
8. PostgreSQL, MySQL, DuckDB, ClickHouse, Trino, BigQuery, StarRocks,
   CockroachDB adapter와 분석용 database 선택
9. Spring Boot, Ktor, Batch, Spring Modulith 통합과 resource ownership
10. jdbc-tests·r2dbc-tests, Testcontainers, 운영, 문제 해결, benchmark 해석
11. persistence와 JaVers audit/history 책임 경계

상세 chapter는 단순 API 열거를 피하고 다음 질문에 답한다.

- 독자가 어떤 문제에서 이 module 또는 통합을 선택하는가?
- JDBC와 R2DBC, cache backend, database adapter 사이의 핵심 trade-off는 무엇인가?
- transaction, dispatcher, connection pool, cache lifecycle, shutdown 책임은 누구에게 있는가?
- 최소 사용 예 이후 production 적용에서 무엇을 추가해야 하는가?
- 대표 source와 test가 계약을 어떻게 증명하는가?
- 실패 시 어떤 증상과 진단 순서를 확인해야 하는가?

## 8. 학습 경로와 저장소 경계

독자는 목표에 따라 다음 경로를 선택할 수 있어야 한다.

- JDBC 입문: `getting-started` -> JDBC transaction/repository ->
  Spring Boot JDBC -> `exposed-workshop`
- R2DBC 입문: R2DBC transaction/coroutine -> Spring Boot R2DBC ->
  `exposed-r2dbc-workshop`
- application recipe: 적절한 guide -> `bluetape4k-workshop`
- audit/history/diff: Exposed persistence 책임을 확인한 뒤
  `bluetape4k-javers`로 이동
- upstream API/변경 이력: JetBrains Exposed 공식 문서로 이동

cross-repository link는 학습 맥락을 설명하는 prose로 작성한다. Exposed가
다른 저장소의 동작을 소유하거나 해당 저장소의 현재 `develop`을 보증하는
것처럼 표현하지 않는다. 링크 텍스트에는 이동 목적과 책임 경계를 함께
적어 독자가 source repository와 workshop을 혼동하지 않게 한다.

## 9. 시각 자산 계약

architecture, transaction ownership, cache selection, database adapter map,
learning path처럼 관계를 문장만으로 이해하기 어려운 주제에는 diagram을
사용한다. 장식 목적의 그림은 추가하지 않는다.

- 승인된 dark technical style을 사용한다.
- source SVG와 rendered PNG를 같은 topic directory에 함께 보관한다.
- 영문 label을 기본으로 두 locale이 같은 asset을 재사용한다.
- release `1.11.0`에 없는 module, API, 연결선은 표시하지 않는다.
- README나 기존 site diagram을 재사용할 때도 release 기준 내용과 endpoint를
  다시 검증한다.
- 모든 diagram은 현재 `bluetape-diagram` checklist를 완료한다.
- 자동 geometry 검사로 clipping, overlap, bounds, 연결선 오류를 확인한다.
- 생성 성공만으로 승인하지 않고 PNG를 원본 크기로 열어 font, label,
  endpoint, spacing, contrast를 눈으로 검수한다.
- 문서 안의 실제 표시 크기에서도 정보 밀도와 가독성을 확인한다.

diagram inventory와 locale embed는 manifest/contract가 검증한다. SVG만 있거나
PNG만 있는 asset, 존재하지 않는 embed, locale 한쪽에서 빠진 diagram은
완료로 인정하지 않는다.

## 10. source-first 게시 순서

게시 단위는 다음 순서를 지킨다.

1. Exposed source repository에서 contract, bilingual manual, assets,
   generated manifest를 구현한다.
2. authoring-tree validator, release validator, export test와 focused docs
   validation을 통과한다.
3. source PR의 review와 CI가 끝나고 source commit이 확정된다.
4. 그 뒤에만 `bluetape4k.github.io`가 source repository, release ref,
   release commit, source commit을 기록한 `1.11` snapshot을 수집한다.
5. site는 snapshot, locale route, version selector, search, latest alias를
   별도 검증하고 게시한다.

사이트 snapshot이 source PR보다 먼저 만들어지거나, 미병합 worktree를
게시 근거로 사용해서는 안 된다. source 수정이 생기면 source PR에서 다시
검증한 뒤 새 source commit을 기준으로 snapshot을 갱신한다.

## 11. 집중 검증 전략

이 작업은 문서 전용 변경이다. production build 전체나 Testcontainers matrix
대신 문서 계약을 직접 증명하는 focused validation을 사용한다.

- Ruby unit tests: authoring contract, release contract, release inventory,
  manifest export, scaffold preservation
- Gradle inventory export와 JSON uniqueness/count 검사
- 정확한 release tag SHA 확인
- stable 40 / develop 42 / 제외 2개 집합 비교
- 40개 module의 영문·한국어 landing 존재와 frontmatter parity
- detailed chapter, source/test/example path, cross-repo prose link 검사
- SVG/PNG pair, geometry, full-size visual review evidence
- generated manifest determinism과 working tree cleanliness
- `git diff --check`와 placeholder/contradiction `rg`

문서 렌더러나 README link를 실제로 변경하는 단계에서만 해당 렌더링/route
검증을 추가한다. 이 설계·계획 커밋 자체에는 Gradle compile, Kotlin test,
site build가 필요하지 않다.

## 12. 실패 처리

다음 조건은 fail closed로 처리한다.

- release tag 또는 고정 commit 불일치
- stable inventory가 40이 아니거나 manifest와 양방향 차이가 있음
- 제외된 develop-only module이 본문, manifest, diagram에 stable 기능으로 등장
- 영문·한국어 landing/chapter/diagram 불일치
- release tree에 없는 repository-relative source/test/example path
- 중앙 consumer version을 Exposed release version과 혼동한 설치 예제
- source SVG 또는 rendered PNG 누락
- full-size visual review evidence 누락
- source PR이 확정되기 전 site snapshot 생성
- generated manifest가 비결정적이거나 기존 내용이 부분 갱신됨

validator 실패 시 마지막 검증된 manual과 site snapshot을 유지한다. 한 단계의
실패를 우회하려고 제외 목록을 넓히거나 링크 검사를 약화하지 않는다.

## 13. 완료 조건

Exposed `1.11` 원본 매뉴얼은 다음 조건을 모두 만족할 때 완료다.

- repository, release ref, release commit, minor가 이 문서의 권위와 일치한다.
- stable 40개 module이 manifest와 두 locale에 빠짐없이 존재한다.
- develop 42개 중 제외 2개가 정확하며 안정판 문서에 유입되지 않는다.
- manual-grade 핵심 경로와 detailed chapter가 단순 scaffold가 아닌 완성된
  설명, 예제, 선택 기준, 운영 주의사항을 제공한다.
- 중앙 `bluetape4k-dependencies` consumer version guidance와 Exposed release
  provenance가 명확히 구분된다.
- release inventory/filter와 release-link validation test가 통과한다.
- cross-repository learning links가 prose로 책임 경계를 설명한다.
- 모든 diagram이 dark style, SVG/PNG pair, `bluetape-diagram` checklist,
  geometry 검사, 원본 크기 눈 검수를 통과한다.
- generated manifest가 결정적이며 source repository가 site ingestion에
  필요한 정규화된 계약을 제공한다.
- focused docs-only validation과 `git diff --check`가 통과한다.
- source PR이 review/CI를 통과해 확정되고, 그 뒤의 site snapshot 작업에
  release commit과 source commit을 넘길 수 있다.

이 조건은 사이트 공개 완료와 구분된다. source repository 완료 후
`bluetape4k.github.io`가 snapshot, bilingual routes, version selector, search,
latest alias, 배포를 검증해야 비로소 공개 완료다.
