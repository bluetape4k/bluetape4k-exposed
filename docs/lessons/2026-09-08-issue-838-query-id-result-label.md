# 엔티티 ID는 결과 라벨로 검증한다

## 원인과 결정

#838의 JDBC raw SQL은 ID 조회 실패와 NULL을 첫 컬럼으로 대체했다.
첫 컬럼이 우연히 ID와 같은 타입이면 다른 엔티티를 조회하거나 빈 결과를 반환했다.
ID 결과 라벨을 행 순회 전에 확인하고 NULL은 별도로 거부한다. 컬럼의 원래 이름이
아닌 결과 라벨을 사용해야 alias로 숨긴 ID를 드라이버마다 다르게 처리하지 않는다.

## 검증과 후속 기준

회귀 테스트의 첫 컬럼을 Long으로 맞춰 기존 구현이 예외 없이 통과하는 RED를
확인했다. Integer를 쓰면 기존 타입 변환 오류가 테스트를 우연히 통과시켰다.
테스트는 예외 발생뿐 아니라 해당 ID 계약의 진단을 확인해야 한다.
사용자 정의 ID, 명시적 ID 위치, 대소문자, 빈 결과와 중복 라벨도 검증한다.

커스텀 H2 fixture에서는 인용된 컬럼과 raw SQL의 대소문자 정책도 일치시켜야 한다.
최초 fixture 실패는 ID 검증 실패가 아닌 `name` 컬럼 조회 실패였다. fixture를
`DATABASE_TO_LOWER=TRUE`로 고정하고 실제 동작의 RED와 구분하여 기록했다.

공통 NULL 검증은 기존 의존성만으로 구현한다. common 모듈에는 support helper
의존성이 없으므로 helper 재사용만을 위해 새 의존성을 추가하지 않고 표준
`requireNotNull`을 사용한다. adapter의 타입 변환과 JDBC metadata 접근은 공통화하지 않는다.
